## 一、项目概述

`xktmcp` 是一个基于 [MCP Go SDK](https://github.com/modelcontextprotocol/go-sdk) 构建的 **学员/员工信息查询 MCP 服务器**，面向 AI 编排平台（如 n8n）提供结构化工具调用能力。服务器支持三种传输协议（`stdio` / `SSE` / `Streamable HTTP`），具备认证、可观测性、缓存、熔断等生产级特性。

**工具参数公共结构（`CommonArgs`）：**


## 四、核心模块分析

### 4.1 传输与启动（`cmd/server/main.go`）

- 支持 **stdio**（本地，免认证）、**SSE**（`/sse` + `/messages/`）、**Streamable HTTP**（`/mcp`）三种模式。
- 日志使用 **Lumberjack** 自动分割（100MB 上限，保留 7 天，gzip 压缩），并启动 goroutine 每天凌晨强制轮转。
- MCP Server 启用 **30s KeepAlive 心跳**（防长连接超时断开）。
- HTTP Server 仅设 `ReadHeaderTimeout`（10s）和 `IdleTimeout`（120s），**刻意不设** `ReadTimeout`/`WriteTimeout`，因 SSE / Streamable HTTP 需要长流式连接。
- 优雅关闭：监听 `SIGINT`/`SIGTERM`，15s 超时内等待在途请求结束。

### 4.2 认证（`internal/auth/`）

多层认证机制，按以下优先级叠加：

1. **IP 白名单（CIDR）**：命中直接放行，无需 Bearer 令牌。
2. **本地静态令牌（`AUTH_TOKEN`）**：`crypto/subtle` 常量时间比较，防计时侧信道。
3. **多租户令牌（`AUTH_TENANTS`）**：JSON 配置，支持每租户独立限速（令牌桶）与工具白名单。
4. **远程兜底验证（`AUTH_REMOTE_VERIFY_URL`）**：正/负结果分离 TTL 缓存，目标主机白名单（防 SSRF），全局限流。

安全特点：
- 令牌只从 `Authorization` 头读取，**不支持 URL `?token=`**（防凭证落日志）。
- 日志只打印令牌掩码，绝不记录原始值。
- 网络传输（http/sse）未配置任何认证方式时 **fail-closed 拒绝启动**；stdio 免认证（本地传输）。

环境变量：

| 变量 | 说明 |
|------|------|
| `AUTH_TOKEN` | 本地静态令牌 |
| `AUTH_TENANTS` | 多租户 JSON 配置 |
| `AUTH_REMOTE_VERIFY_URL` | 远程验证端点 |
| `AUTH_REMOTE_ALLOWED_HOSTS` | 远程验证允许访问主机白名单 |
| `AUTH_IP_ALLOWLIST` | CIDR 白名单（逗号分隔） |
| `AUTH_TRUST_FORWARDED_HEADER` | 是否信任 X-Forwarded-For |

### 4.3 缓存（`internal/tools/cache.go`）

自研 **`MemoryCache`**，具备三重内存保护：

1. **TTL 惰性过期**：`Get` 命中过期项时即时删除。
2. **后台 janitor goroutine**：每分钟扫描清理「只写不再读」的过期 key，防慢性泄漏。
3. **LRU 容量上限**（默认 1024 条）：超限即从尾部淘汰，保证内存有硬上界。

全局只有一个 `sharedCache` 实例，各工具用 `"<tool>:<op>:<参数>"` 命名空间隔离键。

### 4.4 上游 HTTP 客户端（`internal/client/`）

**熔断器（Circuit Breaker）**：

| 状态 | 说明 |
|------|------|
| `Closed` | 正常放行，累计连续失败计数 |
| `Open` | 连续 5 次失败后打开，10s 冷却期内快速失败（不打后端） |
| `Half-Open` | 冷却期满后放行 1 个探测请求，成功恢复/失败重新打开 |

**重试策略**：指数退避（100ms → 200ms → 400ms），最多 3 次，仅对 5xx 和网络错误重试。`context.Canceled` 不计入熔断失败（中性），`DeadlineExceeded` 计为失败（后端挂起信号）。

### 4.5 RAG 知识库检索（`internal/tools/rag.go`）

**语义查询改写**（双层降级）：

1. **MCP Sampling（LLM 改写）**：`rewrite=true` 时，通过 MCP `session.CreateMessage` 调用客户端 LLM 改写查询，专业性更高。
2. **本地规则改写**（降级）：
   - 客户端不支持 sampling（Method not found）→ 进程级标记，后续直接走本地规则，避免重复无效往返。
   - 环境变量 `RAG_SEMANTIC_REWRITE=false` 全局关闭语义改写。
   - 本地规则处理「怎么处理」→「处理规则」、「如何处理」→「处理规则」等口语化转换。

### 4.6 可观测性

| 组件 | 实现 |
|------|------|
| 结构化日志 | `internal/logger`，支持 `InfofCtx`、`ErrorfCtx`、`ToolfCtx`、`APIfCtx`、`AuditCtx` |
| 审计日志 | 记录工具名、查询者(querier)、被查主体(已脱敏)、状态、耗时、trace_id |
| Prometheus 指标 | `internal/metrics`，暴露于 `/metrics`；记录工具调用量/错误数/耗时 |
| TraceID | `internal/trace`，从 `toolCallId`/`sessionId` 生成，贯穿全链路 |
| PII 脱敏 | `internal/pii`，手机号/证件号掩码，响应数据统一过滤 |

### 4.7 统一埋点（`internal/server/register.go`）

`addTool[In auditable]` 泛型函数包装每个 MCP Tool Handler，提供：
- TraceID 注入（从参数取或新生成）
- Prometheus 指标上报（调用量/耗时/状态）
- 审计日志（谁/用什么工具/查了谁/结果/耗时）
- 摘要日志（status + latency）

工具调用者只需关注业务逻辑，埋点完全透明。

## 七、运行方式

```bash
# stdio 模式（本地，供 AI 客户端直接调用）
go run ./cmd/server/main.go

# Streamable HTTP 模式（生产推荐）
go run ./cmd/server/main.go -transport=http -port=8081

# SSE 模式
go run ./cmd/server/main.go -transport=sse -port=8081

# 调试详细日志
go run ./cmd/server/main.go -transport=http -port=8081 -debug

# 生产 Linux 二进制构建
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build \
  -trimpath -tags=jsoniter -ldflags="-s -w" \
  -o mcp-server ./cmd/server/main.go
```

## 九、优化建议

### 9.1 安全

- [ ] `AUTH_TENANTS` 配置中的 `token` 字段建议支持哈希存储（目前为明文），避免 JSON 配置泄漏导致令牌直接暴露。
- [ ] `/metrics` 端点目前无认证保护，建议在生产网络层隔离或添加访问控制。

### 9.2 功能扩展

- [ ] **`student_search` 分页支持**：当前只返回第一页结果，对于同名学员较多的场景，建议增加 `page`/`limit` 参数。
- [ ] **RAG 多知识库路由**：`rag_search` 目前调用单一知识库，可考虑按 `userId` 租户路由不同知识库。
- [ ] **工具级限流**：`addTool` 统一埋点层可加入每工具的请求速率控制，防单工具被滥用。

### 9.3 可观测性

- [ ] **链路追踪**：TraceID 目前仅在日志中传播，可集成 OpenTelemetry 输出到 Jaeger/Zipkin。
- [ ] **缓存命中率指标**：`sharedCache` 的命中/未命中统计目前只在日志中，建议增加 Prometheus Counter。

### 9.4 工程质量

- [ ] `tools/schema.go` 中 `publicSchema` 函数可补充单元测试，验证 JSON Schema 结构正确性。
- [ ] 建议添加 CI 配置（GitHub Actions），自动运行 `go test ./...` + `go vet` + `golangci-lint`。

## 十、总结

`xktmcp` 是一个设计较为成熟的生产级 MCP 服务器，主要亮点：

- **分层清晰**：client → service → tools → server，职责边界明确。
- **安全性强**：多层认证（fail-closed）、常量时间比较、PII 脱敏、SSRF 防护一应俱全。
- **韧性设计**：熔断器 + 指数退避重试，保护上游 API 不被雪崩冲击。
- **可观测性完备**：结构化日志、审计留痕、Prometheus 指标、全链路 TraceID 贯穿。
- **内存安全**：自研 LRU + TTL + janitor 三重保护，无内存泄漏隐患。

当前阶段最值得关注的改进方向是：**多租户令牌安全存储**、**缓存命中率可视化**，以及 **CI 自动化** 接入。
